# Alexandria Front-End v3

Target: `packages/web-client-v3`. Visual system: `@../packages/web-client-v3/DESIGN.md`
("The Noir Imprint"). Product truth: `@../PRODUCT.md`.

v3 replaced `web-client-v2` in production at `alexandria.isnan.eu`. **v2 is an explicit
anti-reference** for identity and IA, and a working reference for what the API returns. The backend
is unchanged.

---

## 1. Technical baseline

| Item | Decision |
|---|---|
| Stack | React 19 + Vite 6 + Tailwind CSS 4 + `vite-plugin-pwa` |
| Auth | `aws-amplify` (Cognito: email/password + Google OAuth) |
| Routing | `react-router-dom` |
| Capture | `@zxing/browser` + `@zxing/library` (ISBN), `react-webcam` (cover OCR) |
| Language | JavaScript only, no TypeScript |
| Install | `yarn --cwd packages/web-client-v3` — own `yarn.lock`, no workspaces |
| Dev server | Fixed port **5173**, the port `packages/infrastructure/cognito.tf` registers as an OAuth callback. Cost accepted: v2 and v3 dev servers cannot run at once. |
| Lint | Oxlint |
| UI primitives | Locally-owned source files, no component-library dependency |
| Deploy | S3 + CloudFront. `frontend-build|sync|invalidate|deploy|serve` point at v3; `frontend-preview` builds against fixtures with no AWS. |
| Config | `output.json` generated by `make infra-output` |

`.jsx` for components, PascalCase filenames, directory-root components as `index.jsx`, double quotes
in JSX attributes and single quotes elsewhere.

**Two suites, with a division that matters:** `yarn test` asserts rules are DECLARED,
`yarn check:browser` asserts they SURVIVE the cascade and that gestures actually fire.
`yarn profile:stream` measures the stream at 1000 items; `yarn profile:search` measures the search
mount.

## 2. Information architecture

| Decision | Choice |
|---|---|
| Home | Libraries list, with search pinned in the header on the root |
| Navigation chrome | **No bottom tab bar.** One stack rooted at `/libraries`; the header carries search and account |
| Settings access | Account plate in the Libraries header → `/settings` |
| Mine vs shared | Two labelled sections in one list: mine first, then "Shared with me", each row naming the owner |
| Collections | Inline groups inside a library, server-grouped, rendered in place with their members. One hierarchy: library → (collection) → item |
| Lending | Surfaced in place wherever an item appears. **No "on loan" overview screen** |
| Adding | Starts inside the library being viewed, so the destination is never asked |

**Why there is no tab bar.** With search pinned in the header and Add living inside a library, a tab
bar would hold only "Libraries" and "Settings" — the two-tab bar whose second tab is Settings.
Removing it frees the bottom of the screen for content and thumb-reach actions. Back is the only
up-navigation.

### The header

One `AppHeader` with a **contextual right slot**, rendered as an `--imprint` plate:

| Screen | Left | Right slot | Search |
|---|---|---|---|
| Libraries root | wordmark | account initials → `/settings` | **pinned field** |
| Library browse | back + library name | add (owned libraries only) | none |
| Item detail (cover) | back | search | slot only, no field |
| Every other built screen | back + its own name | per screen | none |

**The header never scrolls, on any screen.** It is a fixed item at the top of a fixed-height flex
column and the content scrolls beneath it — `DESIGN.md` §4, *The shell, and what scrolls*, owns the
mechanism.

**A built screen carries its own name, never the wordmark.** The wordmark beside a back control was a
transitional stub construction for screens with no title worth printing; a finished screen showing it
is announcing it has nothing to call itself.

**The pinned field belongs to the root and nowhere else.** The dominant job — "do I own this?" —
starts from a cold open, which lands on the root, where the field is the loudest mark on screen.
Entering a library is a different intent: browsing what you already chose.

A field on a browse screen would be the loudest thing there and would promise to *leave*, since it
searches every library. **Scoping it to the current library was considered and rejected:** the API has
no scoped search, so scoping means filtering a global response, which hides matches elsewhere and then
needs a second control to un-hide them — a limitation invented in the client and then worked around in
the client. Global search prints each result's library name, so nothing is lost.

Cost accepted: from inside a library there is no fast path to a title. One tap back reaches the field.

### IA anti-patterns, and what replaces each

| Anti-pattern | Refused by |
|---|---|
| Hub-and-spoke forcing a library choice before you can look anything up | Search is pinned on the root and spans every library |
| A tab bar where Settings is a peer of the collection | No tab bar. Account plate in the header |
| Two competing hierarchies — collections as a parallel tree | Collections are inline groups from the API's own server-side grouping. There is no collections destination |
| Read-only expressed as a screen full of disabled buttons | On a shared library, actions are **absent**, not disabled, and provenance is declared in the header |
| UI implying data the backend lacks (genres, tags, ratings, due dates, sort-by-date, "recently added") | Nothing references a field the API does not return. See §6 |
| Icons carrying state with no text | Every state carries words: `OUT · <name>`, `SHARED · 3`, `FROM Marie` |
| Infinite scroll with no sense of position | Sticky Index Letters mark alphabetical position; pagination stays invisible |
| Detail as a modal that cannot be linked or refreshed | Item detail is a real route, resolvable in one request. Survives refresh and PWA restart |
| A global "+" that then interrogates you about the destination | Add lives inside the library |
| Destructive actions confirmed only by a toast you can miss | Destructive actions confirm in place, before acting |
| Repeating the same fact in several places at once | "Nothing is labelled twice" is binding |

### `AddFlowLayout` — the layout route

`src/components/AddFlowLayout.jsx`, wired in `src/routes.jsx`, wraps the four add-flow routes
(`add/book`, `add/book/results`, `add/video`, `add/video/results`). It has no path segment of its own
and renders only an outlet, so those four keep the exact URLs above. What it owns is a **span** — the
two things whose lifetime is precisely *the reader is cataloguing*. The two are **composed, not
merged**: folding the camera lease into the session provider would make a component named for counting
saved items also responsible for turning a device off.

**The filing session's identity.** `FilingSessionProvider` holds how many items this session has
filed, and "session" is defined by nothing except where that provider is mounted: across capture →
results → capture, however many loops, and unmounted the moment the reader leaves the flow. No timer,
no storage key to expire. Two alternatives are recorded as worse. `location.state` is not the channel
this flow's **identifying inputs** may travel in — the code or title looked up, and the collection
being filed into, ride in the query so a cold load can resume from the URL alone. State is not barred
outright: it carries what is safely recoverable, which is why candidates already paid for ride to the
results screen in it, tagged `forIsbn` or `forTitle`. **On the hop to results both capture screens
assert the state EXACTLY, and non-empty** — those candidates and nothing else — which is what catches a
wholesale `location.state` forward riding on top of an already-correct query. Adding a tally would mean
loosening those probes for a decoration. `sessionStorage` survives too much.

**The camera lease, on that same span.** A capture screen borrows the shared stream and never stops it,
because every save remounts that screen and stopping it there made each item pay for a fresh
`getUserMedia` and a sensor warm-up. Leaving the flow unmounts this layout and turns the camera off.
**Backgrounding the app releases it too** (`visibilitychange`), which is what makes the trade
defensible in one sentence: *the camera is open while the reader is inside the add flow **and** the app
is in front of them.* Re-attaching belongs to whichever viewport is on screen, since only a component
holding a `<video>` can do it; the results screen correctly needs nothing. No grace window is possible,
because the gap between leaving capture and returning is however long choosing takes.

**The release is deferred by one macrotask, and not as a grace window.** React StrictMode
double-invokes mount effects in development, so an immediate release stopped the stream the first mount
had just acquired. A remount cancels the pending release; a real unmount lets it fire on the next tick.
The pending handle sits at module scope because it has to survive an unmount-and-immediate-remount,
which is the case it exists for.

## 4. Screen specification

### Login — `/login`
Imprint wordmark plate, email and password fields, primary Plate Button, Google action as a ruled
secondary, link to `/signup`.
**States:** idle; submitting; invalid credentials; `UserNotConfirmedException` → "pending approval";
OAuth callback outcomes read from URL params — account **linked** (success: "sign in again"),
`user already exists`, generic `error_description`.
**API:** Amplify `signIn`, `signInWithRedirect`.

### SignUp — `/signup`
Email, display name, password with live complexity checks.
**States:** idle; submitting; `UsernameExistsException`; PreSignUp rejection; success → returns to
`/login` with an account-created confirmation.
**API:** Amplify `signUp`.

### PendingApproval — conditional
A full-page stamped notice: the request is with an administrator. Sign-out is the only action. No
polling — approval arrives out of band (Slack or the admin CLI), so the honest instruction is to sign
in again later. Reachable in mock mode via `?as=pending`, since it is not a route and nothing else can
render it.

### Libraries — `/libraries`
Header: imprint wordmark, pinned Search Field, account plate. Body: two labelled sections — mine, then
"Shared with me". Each library is a numbered volume: name, item count in a plate, Shared Ribbon when
relevant. Primary action: new library, in a bottom bar.

Owned rows carry a **Row Actions** affordance — the visible duplicate long-press requires — opening
the LibraryActionsSheet: Edit, Share (inline email form), Unshare, Delete (confirm in place).
Shared-with-me rows have no long-press **and no affordance**, which is how read-only declares itself.

`sharedFrom` is a Cognito username, which for a native signup **is the user's email address**, so a row
reads `FROM marie@example.com`. The address is content, never uppercased. `READ ONLY` is not printed:
the green `FROM` tag and the absent actions already say it.
**States:** loading skeletons; empty (ruled invitation at full weight); error inline; pull-to-refresh.
**API:** `GET /libraries`.

### NewLibrary / EditLibrary
Name (≤20) and description (≤100), with live remaining-character counts.
**API:** `POST /libraries`, `PUT /libraries/{libraryId}`.

### UnshareLibrary — `/libraries/:libraryId/unshare`
Recipients with multi-select, 1–10 per request. Bar states per `DESIGN.md` §6.
**API:** `POST /libraries/{libraryId}/unshare`.

### LibraryBrowse — `/libraries/:libraryId`
The core screen. Header: library name, back, add (owned only); shared libraries carry provenance and
**no** add.

Body: a single stream of Volume Frames in **the server's order, never re-sorted client-side**, with
sticky Index Letters. The alphabet is the server's folded one and is not strictly A–Z.

Collections arrive as `type=2` entries and render as Collection Boards, filed alphabetically under the
collection's name with members in `order`. A board flagged `partial` on a continuation page **merges
into the board already on screen** — the reader ends with one board holding all its members, and no
label is needed because nothing was split in their view. Rendering a second labelled board would show
one collection twice, which reads as a data bug. The API emits the partial board first on the
continuation page, so the merge target is unambiguous. A partial board with no predecessor keeps its
flag and reads `CONTINUES`.

Every frame is portrait 2:3. **Type is not marked** (`DESIGN.md` §4). Lent items carry the Overprint
Stamp. Tapping the header title scrolls to top. Long-press an owned item → ItemActionsSheet: Edit, Lend
(inline name form), Return, Delete.
**States:** loading; empty; end-of-list; error; pull-to-refresh; infinite scroll appending pages at 30.
**API:** `GET /libraries/{libraryId}/items?limit=&nextToken=` (limit ≤50);
`GET /libraries/{libraryId}/collections`.

### NewCollection / EditCollection
Name (≤100, unique per library) and description (≤500). Duplicate-name rejection is surfaced **on the
field**, branched on **status 409** — never on a regex over the server's prose.
**API:** `POST|PUT /libraries/{libraryId}/collections[/{collectionId}]`. Deletion **orphans** members
rather than deleting them, and the confirmation says so plainly.

### AddBook — `/libraries/:libraryId/add/book`
Live camera scan (EAN-13/EAN-8) and manual ISBN entry in one screen. A visible manual-entry escape is
always present, for denied permission, poor light or a damaged barcode. Continuous scanning: after each
save, return here for the next item.

**States:** requesting permission; permission denied → manual only; scanning; decoding; submitting;
no-result → offer manual entry at `/items/new/book`.

**"No result" is NOT `candidates.length === 0`.** `services/resolvers/google.go:81-88` emits **one
candidate carrying `error`** when `totalItems == 0`, and `tmdb.go:150-158` does the same — and video
has a single resolver, so a film miss is *always* exactly one errored candidate. Only Babelio and
GoodReads return an empty array. A `length === 0` test therefore never fires on a real miss and the
reader is shown a screen of failures with no way forward.

**The predicate is "no candidate without an error".** A zero-length response is a different condition —
every resolver failing at the request level — and is a transport failure rather than a miss. Both lead
to manual entry; only one says "we found nothing matching that".
**API:** `POST /detections` with `type: 0` and `code`.

### BookDetectionResults — `/libraries/:libraryId/add/book/results`
Candidate volumes from Google Books / Babelio / GoodReads, each with its source and its own possible
`error`. Per the **preview-before-commit** discipline, nothing is filed until the reader confirms a
candidate, and a per-resolver failure is shown rather than silently dropped. Each candidate carries its
artwork in the 88×132 `candidate` Volume Frame — ruled and empty when a resolver supplies none —
because on this screen the picture is what decides the match.
**API:** `POST /libraries/{libraryId}/books`.

**`USE THIS` is the primary plate — the accent belongs on the commit, not on the fallback.** Filing a
candidate is the flow's only write; the re-search stays `secondary`, so redo and commit do not look
identical.

**Candidate counts, for anyone reasoning about list length.** Film is capped at **5** by
`services/resolvers/tmdb.go:161` (`maxResults := 5`) — **our line, not TMDB's**, and someone could
delete it without knowing a visual ruling rests on it. Book has **no cap anywhere**: Babelio and
GoodReads emit at most one each, and `google.go:92-106` appends every item with no `maxResults`
requested, so Google Books' default page size of 10 governs. Theoretical worst case 12. **Capping
Google in the resolver is refused as a route to a visual outcome** — it is a product decision about
whether to hide volume records, and `PRODUCT.md` binds this rework to require no endpoint changes.

**A failed resolver is a NOTE, not a candidate, and must never be given a title.** It renders as a
ruled note: no frame, no title role, no `USE THIS`. One line in the failure register naming the source
and what happened — `BABELIO — NO ANSWER` — grouped after the real candidates. As built it rendered a
full candidate row titled **`Untitled`**, which is fabricated content in the slot a reader scans first,
and on a true miss (exactly one errored candidate) it put a volume called `Untitled` directly above
`NO MATCH FOUND` — one screen making two opposite claims, the fabricated one louder.

**The scanned code belongs once, at the head, in the mono** — every candidate carries the same ISBN by
construction, so printing it per row is the reader's own input echoed three times.

**A results screen must survive a refresh, and the query string is what makes that possible.** A
results screen holding candidates only in `location.state` is the "detail as a modal that cannot be
refreshed" anti-pattern wearing a route. A cold load would arrive with no candidates and, worse, **no
collection**, so a reader who had chosen a board would resume filing standalone without being told. So
the identifying input travels in the **query**: `?isbn=` and, when filing into a collection,
`?collectionId=`. A cold load re-runs `POST /detections`, which is a read with no side effects.

**Video is not asymmetric.** `handleVideoDetection` resolves a typed title and an OCR-extracted title
into one `searchTitle` and calls the identical `h.s.ResolveVideo(searchTitle)`, so candidates are a pure
function of the string. Once OCR has produced a title there is no photograph in the recovery path.
**Every navigation to that route carries `?title=`**, typed or extracted. The correct narrow statement:
the *capture* cannot be carried, so a cold load **before a title exists** has nothing to resume.

**Both results routes keep a no-input branch** — a bare URL with no `?isbn=` / `?title=` is reachable by
typing or sharing it — redirecting to the capture screen with a printed line. One construction, both
screens, type-agnostic, and **it must not mention an image**: nothing was lost, there was simply never
anything supplied. Neither screen ever renders an empty candidate list as a spinner that never resolves.

### AddVideo / VideoDetectionResults
Cover capture via manual shutter (OCR through Bedrock/Claude vision) or a typed title. Results are TMDB
candidates: title, year, runtime, director, cast, poster.
**API:** `POST /detections` with `type: 1` and `image` or `title`; then `POST /libraries/{libraryId}/videos`.

**The capture is ONE action, because `/detections` is atomic.** The endpoint takes an image, runs OCR,
searches TMDB, and returns **candidates *and* `extractedTitle` in one response**; there is no OCR-only
endpoint. A capture → review title → search flow can only be built by calling `/detections` with the
image, keeping `extractedTitle`, **discarding the candidates already paid for**, and calling
`/detections` again with the title — two detection calls per film, one including a base64 upload and a
vision invocation, its result thrown away. The shutter completes the job: one tap, one call, straight to
the candidates.

**The review step moves rather than disappearing.** OCR is fallible, so the extracted title is an
**editable field on the results screen** that the reader can correct and re-search. That puts the cost on
the failure path. Seeing the candidates is also a better signal of OCR failure than reading the bare
string.

**The labels must name their outcome.** The shutter reads **`LOOK UP THIS COVER`**; the text field's
action reads **`LOOK UP THIS TITLE`**. A bare `Capture` would do more than it says. The underlying defect
was structural, not merely wasteful: `Capture` populated a field owned by a *different* button, so its
consequence appeared elsewhere and needed a second, differently-labelled action to mean anything.

Frame geometry, the aiming argument and the capture-region fix are in `DESIGN.md` §4, *The two capture
viewports*. Narration is in `DESIGN.md` §5, *Capture Caption*.

**Disabling during an in-flight lookup is deliberately NOT part of this**, by the owner's decision. The
residual, stated so it is not rediscovered: a tap or decode during an in-flight lookup is swallowed by
the `if (isBusy) return` guard, and on the film screen the shutter can be tapped during a *title* lookup
where it is not the narrating control. Accepted because some control on screen is visibly narrating in
every such case.

### NewBook / NewVideo — manual entry
Full forms honouring the API's limits: title ≤100, summary ≤4000, authors; or directors ≤100 each, cast,
`releaseYear` 1800–2100, `duration` 0–1000 minutes, `tmdbId`.

**The collection pre-selection travels in `?collectionId=` here too — the query wins everywhere.** When
`Enter by hand` is reached from a collection board, the form seeds its picker from the query, not from
`location.state`, or a cold load silently resumes filing **standalone**. The counter-argument — that on a
form the loss is *visible*, since the picker sits on screen reading `None` — does not hold: **visibility
is not recovery.** A reader cannot tell they *had* chosen a board rather than simply never choosing one,
and `Collection` sits low on a form that scrolls. The argument that settles it needs no per-screen
judgement: **a rule requiring "visible enough" on each surface will be applied inconsistently.**

**Where the picker exists, it IS the filing mark — do not print `FILING INTO` as well.**

**Collection invariant, and it is one-directional.** An **order without a collection** is rejected
(`handlers/items.go:31`). A **collection without an order is not**: `handlers/items.go:36` comments
"Order is optional - will be auto-calculated by service layer if not provided", and `services/items.go`
sets `order = maxOrder + 1` from `GetMaxOrderInCollection`. An empty collection yields `maxOrder = 0`, so
its first item gets `1`. Server-side ranking is strictly better than anything the client could do: the
collection endpoint returns `itemCount` but **not its members**, so a client computing `itemCount + 1`
would collide in any collection containing a gap.

**The order field stays on every form** — a reader must be able to re-rank an item after filing. What
changes is when it may be empty, distinguished exactly by comparing the selected `collectionId` against
`initial.collectionId`:

| Case | Order | Empty means |
|---|---|---|
| New item, collection chosen | optional | file it last; the server computes the rank |
| Edit, collection **changed** (including newly set) | optional | file it last in the new collection |
| Edit, collection **unchanged** | **required** | nothing — and clearing it is a hazard |

The third row needs care. `services/items.go` auto-calculates only when `isNewToCollection`
(`oldCollectionId != newCollectionId`), so on an item staying in its collection, omitting `order` sets it
to nil rather than re-ranking. `internal/persistence/models.go:96-101` then returns the no-collection sort
key `item#<title>` whenever `order == nil || *order < 1`, regardless of collection — while grouping is a
**two-pass lookup keyed on `CollectionId`** (`api/repositories/dynamodb/items.go:813`), so the item is
still pushed into its collection's bucket and nested **only if the collection's header lands on the same
page**. The same record therefore renders as a nested member on one page and a loose row on another —
page-dependent and non-deterministic — and it breaks the `itemCount > len(items)` bookkeeping driving
`partial`. The form keeps order required in that case, using `DESIGN.md` §6's **second** form (the reason
in the control's position).

Order remains 1–1000 whenever supplied.

### ItemDetail — `/libraries/:libraryId/items/:itemId`
The one screen on the black cover, and **the one screen where artwork earns real space**: the hero
carries the cover in the same undecorated 2:3 frame at 132×198, ruled in `--paper`. With no artwork it
stays the ruled empty frame — a designed state, not a placeholder.

Beside the frame, in the column that was otherwise dead space, the **Detail Marks**: `IN <library>`
linked to that library; the Shared Ribbon when the library is shared either way; the Overprint Stamp when
the item is out. The link matters most when the reader arrived from search. The library is **not** in the
Plate Line, and `--shared` fails as text on the black cover.

Then title, Plate Line, the yellow rule, and — per the **record-carries-its-past** discipline — the loan
ledger inline: the first page of events paired into loans. "Full record" continues to `/history`.

Loan state is stated **once**, by the stamp. No "Currently out" label above it.

**Actions are laid out by what they are, not gathered behind one control:** the circulation action
primary, then `Edit`, then `Delete`, all three on one line, each in its own treatment — filled plate, ink
outline, `--out` outline — with the destructive one confirming in place. `Mark returned` is a button that
marks returned; `Lend` opens a sheet only because a borrower's name is required, and that sheet contains
**only** the lend form.

**Rank destructive actions by treatment, not by distance.** `Delete` dropped to its own row below the
ledger reads as though it deletes the *record*, which is a real action this app offers elsewhere. Grouped
with Lend and Edit it can only mean the item.

Deep-linkable and refresh-safe in one request. `404` renders a stamped "not in this collection" notice,
not a spinner that never resolves.
**Cache-busting:** thumbnails load as `picture?v={updatedAt}`.
**API:** `GET /libraries/{libraryId}/items/{itemId}`, `GET .../events?limit=`.

### EditItem — `/libraries/:libraryId/items/:itemId/edit`
Pre-filled; the same form bodies as New. Because `PUT` returns an empty body, the item is **re-read**
after saving, and the row is **replaced, never merged** (§6).
**API:** `PUT /libraries/{libraryId}/books|videos/{id}`, then `GET .../items/{itemId}`.

**The header names the type from the first frame, and the type travels in `location.state`.** The
title is `Edit book` or `Edit film`, which is known only after the fetch — so the screen printed
`Edit item` and then corrected itself a beat later, a visible flicker on every edit. Both openers,
`ItemActionsSheet` and item detail's `Edit`, hold the whole record when they navigate, so they hand
the type over and nothing has to be guessed.

**This does not contradict §3's ruling that the add flow's inputs may not ride in state.** That rule
governs **identifying** inputs — the code or title looked up, the collection being filed into — which
a cold load must be able to resume from and therefore belong in the query. The type here identifies
nothing: the URL alone still resolves this screen, and the fetch that follows re-establishes the type
as fact, which is why **the fetched value overrules the hint** rather than trusting it. Read it with
`??` and never `||`: a book is type `0`.

**With no opener there is no hint, and then the header prints NOTHING rather than a guess** — the
construction `LibraryBrowse` already uses for a library name it has not fetched. The `<h1>` keeps
`Edit item` in that gap, because an unnamed landmark is a defect where a quiet header is not.

**The wrong word stays up for as long as the SLOWER of two requests**, since the mount fetches the
item and the collection list in one `Promise.all`. Splitting them was considered and refused: it would
let the form render before its collection picker has its options, trading a title that corrects itself
for a select that gains options — and changes its shown value — under the reader's eye.

**The form carries no cover control of the "fetch again" kind.** A checkbox reading *"Fetch the cover
again from its source"* could not be used correctly by anyone: `pictureUrl` is written by detection and
the reader cannot change it, so re-fetching returns the identical image in every case **except one the
reader has no way to detect** — a thumbnail the asynchronous pipeline failed to produce.

**In its place, `pictureUrl` is a real field on `NewBook`, `NewVideo` and `EditItem` alike.** Detection
frequently returns no cover at all, and **the case with no source is the one that most needs a control**;
gating the replacement on `pictureUrl` existing would exclude exactly the readers who need it.

- Labelled `COVER IMAGE`, pre-filled with whatever detection supplied, empty when it supplied nothing.
  **The source is never named** — the reader cannot act on which resolver produced it.
- Set in the **sans**, not the mono: a URL is not a numeral.
- Changing it and saving sends the new `pictureUrl` with `updatePicture: true`. Clearing it sends `null`.
- Obvious rejects (not `http`/`https`) fail inline, since the fetch is server-side.
- It sits **immediately after `SUMMARY`, before the type-specific block**, so the form reads as *facts
  about this object* then *facts about what kind of object it is*.

**The repair case stays separate**, because it is a different failure. A cover that is *correct but did
not arrive* keeps its own control: `Fetch cover`, attached to the item-detail frame, shown only when a
`pictureUrl` exists **and the image failed to load**.

Three rules fall out. **An action belongs where its problem is visible, not in the form that owns the
field.** **A control that cannot be chosen correctly should not be offered** — detect the condition rather
than word the question better. And **check which case a gate excludes, not only which it admits.**

### ItemHistory — `/libraries/:libraryId/items/:itemId/history`
Paginated events as Ledger Rows on a checkout card, paired client-side into loans. An open loan is
stamped. Clearing the history confirms in a sheet and states that it removes the whole record.
**API:** `GET|DELETE /libraries/{libraryId}/items/{itemId}/events`.

### Search — `/search`
The full-screen surface the header field opens, returning the reader exactly where they were.

**The query runs on submit, never as it is typed.** A 300ms debounce spends a request per pause rather
than per intent — `roman` at an ordinary pace costs three requests to answer one lookup, on the poor
signal `PRODUCT.md` names as the dominant scene. Two triggers, both on the field: the keyboard's action
key (`enterKeyHint="search"`) and the magnifier, which returns now that it has something to do.

A submit below 3 characters prints why; under the debounce that state was invisible, and an explicit act
answered with silence reads as a broken search. Emptying the field drops `?q=` and returns the surface to
its recents — **because the recents are otherwise unreachable**, rendering only in the idle state.

**`?q=` moves with navigation, in both directions.** It was write-once, so Back restored the *previous*
query and its results.

Results are on-paper rows spanning every visible library, each naming its library via `SearchRowMarks`,
since here the shelf **is** new information. Owned results long-press to the ItemActionsSheet and update
in place; shared results do not. Recent searches persist in `localStorage`.
**API:** `POST /search`.

**The result set is unpaginated, and a large one is the LIKELY shape of a short query.**
`api/services/search.go:72` builds `bluge.NewAllMatches` with no size and no top-N, and **each term
contributes a prefix wildcard** across the five fields `internal/searchindex/searchindex.go:31` lists.
On a catalogue deliberately half French, `les`, `des` and `une` are common leading tokens. No sort or
filter controls, since the API offers none.

**A large result set used to fail outright, which is why this paragraph matters.** The matched keys went
to a single `BatchGetItem`, and DynamoDB rejects more than **100** keys per call with a
`ValidationException` — so the short-query case this paragraph describes returned a 500 rather than a long
list. The repository now splits at that limit (`api/repositories/dynamodb/batch.go:13`) and retries what
comes back in `UnprocessedKeys`, **erroring rather than returning silently short results**: a search that
quietly drops rows tells a reader they do not own something they do, and nothing surfaces the loss.

**Windowing is REFUSED, measured.** Scrolling 400 results is p95 **10.3ms** with **zero** frames over
budget, unchanged at 4× throttle and better than the browse stream's 24.2ms, because search fetches
nothing while it scrolls. Windowing exists to fix scrolling and there is nothing here to fix. The whole
cost is **one commit the reader is already waiting through**: 400 rows arrive as a single ~110ms frame,
~327ms at 4×, roughly linear at ~0.27ms/row (~0.8ms throttled). `content-visibility` measured inert here
too (−1%, −3%), a second confirmation on a different workload. **Do not reinstate windowing without a
measurement that contradicts these.**

**A result row is a stream row, not a new invention** — the 2:3 frame, the title, the Plate Line, the lent
stamp and the `--out` edge all arrive unchanged. What it adds is the library.

**The honest limits print at the zero-result state and nowhere else.** Printed permanently they are noise
on every successful search; at zero they prevent the one wrong conclusion this screen can produce — *I
don't own it* — when the truth is *we did not look there*. The empty result says what was searched and
what was not: title, authors, directors, cast and collection, **not the summary and not the ISBN**.

**Accents are folded by the server, on both sides, so there is no accent caveat to print.** The index
and the query both run `NormalizeForMatching` (NFD → strip combining marks → NFC → lowercase), so
`elephants` reaches `éléphants` regardless of how many accents are missing, and `NewFuzzyQuery`'s
`fuzziness: 1` is left to do what it is for — typos. **French elision is split on both apostrophe
forms**, so `ambre` reaches *Les 9 Princes d'Ambre*; before that it returned *En pleine ombre*, a
different book one edit away, which is the failure shape this screen exists to prevent. The
zero-result block previously carried
*"one missing accent usually still finds a title, two do not"*, which described fuzziness standing in
for a fold; it is removed rather than reworded, because **a caveat that no longer holds is worse than
none** — it teaches a reader to distrust a spelling that works.

**The client still must not fold accents itself.** The reason changed but the ruling did not: the client
would have to reproduce the server's fold byte-for-byte, and any drift silently stops matching. Same
reason the stream's letters never use `localeCompare`. This does leave recents holding `etranger` and
`étranger` as two entries that now return identical results — a wart, recorded, nobody's ask.

**An invitation and a limitation are not the same sentence.** An invitation says what to do; the limits
explain a result the reader did not expect. One belongs where nothing has happened yet, the other only
where something has — so the idle surface must **not** restate what search covers.

**No result count.** Apply the test: its absence produces **no wrong conclusion** — the reader scrolls. On
the dominant case of a specific title returning one to three rows it is a line of noise on every search.
There is no size at which this screen breaks and needs to say so. If one is ever wanted it must be argued
from **the commit**, not from scroll performance.

**Recents collapse a prefix, asymmetrically.** When a term is recorded, drop any existing recent that is a
prefix of it — that removes typing artefacts, which are always prefixes, while keeping a *later*
deliberate shorter search. Case is folded; **accents are not**, which no longer matches the server and is
recorded above as a known wart rather than a rule. At most five, most recent first, each a catalogue tag
that re-runs its term. One `Clear` control, no confirmation.

**Results arrive ranked by relevance, most relevant first.** Bluge scores every match; the service sorts
on that score and the repository re-applies the order after the DynamoDB fetch, which answers in no
order of its own. Until that landed the score was discarded and results arrived effectively arbitrary.
The client neither re-sorts nor displays the score — a number a reader cannot act on.

**The search header carries its own name, and that name is inert.** It shipped as back-and-nothing —
the transitional stub shape §2 condemns, on a finished screen — so it now takes `Search` like every
other built screen. What it does **not** take is `LibraryBrowse`'s tap-to-scroll-top. That gesture
exists there because the stream is alphabetical and the top is a place. Here the top is now *the best
match*, which is a stronger claim than the old "an order `POST /search` does not define" — and it still
does not earn the gesture, because the problem scroll-to-top would solve is already solved by the
sticky field. **A title is not an argument for the gesture** — the two travelled together only because
`LibraryBrowse` happened to have both.

**The item-detail search plate links to a bare `/search`, deliberately.** A reader may have reached that
item by browsing and would otherwise be handed their own past query as though they had asked for it. A
reader who arrived from search presses **Back**, which restores their query exactly.

**Repetition that varies is not "labelled twice".** Six results printing `IN Fiction` is not the `TMDB`
badge repeated down five film candidates. That badge was a **constant**; the library **varies** across a
result set and is the field answering *which shelf*. Grouping results by library would also invent an
order `POST /search` does not define.

### Settings / Account / About
Settings: Account, About, Sign out. Account: initials plate, email from the JWT **with a copy Mark beside
it**, captioned with what copying it is for, then the password change with the same complexity rules as
signup. About: version and build hash.

**The copy affordance is on the EMAIL.** Sharing is by email — `POST /libraries/{libraryId}/share` takes
an `email` — so copying your own address has a real job: you send it to someone so they can share a
library *to* you. That is v2's caption and v2's reasoning, and it is right. The copy is a **Mark**, not a
labelled button: copy sits in the universal-affordance family, the caption already says what it is for,
48px target, negative-margined, `aria-label` naming the address.

**`custom:Id` is not on this screen.** It was specified here as "the owner id used for support", and that
use was invented — this product has no support channel, the admin is the owner, the CLI's `users list`
prints ids, and the approval alert carries the email. Printing it would spend the screen's most prominent
line on a 32-character string whose only honest caption would be *this is not for you*.

**The password section is ABSENT for a federated sign-in, not disabled.** A Google account has no password
in this pool.

**Test the `google_` username prefix, never `identities`.** A native signup that later signs in with Google
is **linked** (`authn-scheme.md:116`), so that reader **has an `identities` entry and a password**, and the
linking call sets `DestinationUser` to the existing username so no prefix is added. Gating on `identities`
would hide the password form from the readers most likely to want it, and hide it silently. Cognito mints
`google_<sub>` only for a user **created by** the provider. **Prefix present ⟺ no password.**

This is the one decision here resting on a contract rather than a measurement, flagged as such; what would
falsify it is a federated user whose username carries no provider prefix. The prefix is load-bearing
elsewhere — the onboarding Lambda's provider normalisation keys on it — so account linking would break if
it were absent. The federated branch is reachable in mock mode via `?as=google`, guarded in both directions.

**A line says the sign-in is managed by Google**, because the **absence needs one sentence here** where
read-only did not: a missing action on a shared row is explained by the `FROM` tag beside it, and nothing on
this screen would otherwise say why.

**Never state what a password change does to other sessions.** Cognito's `changePassword` leaves refresh
tokens intact; revoking them is `GlobalSignOut`. Telling a reader their other devices are secured when they
are not is a claim they **act on**, by deciding not to sign out elsewhere.

**Sign out does not confirm.** It destroys nothing. But it is not a navigation row either: a **ruled
secondary Plate Button set apart from the rows**, with a line stating the consequence — *you will need to
sign in again* — which is honest, since a refresh token lasts a year.

**Nothing implies account deletion.** The API has no endpoint for it; it exists only in the admin CLI.

**About carries the version and the build hash, and says what they are for**: so a reader can tell an admin
which build they are on. Without that sentence it is decoration. The hash sits in the **sans** — a short
hash is hexadecimal, mostly letters, and the mono is reserved for numerals.

## 5. Flows

**Add an item.** Library → add → Book or Film (sheet) → capture (scan / OCR / manual) → candidate list →
confirm → saved → back to capture for the next item. Cancel at any point returns to the library. Nothing
is written before the confirm step.

**Lend and return.** Long-press item → Lend → name → saved; the Overprint Stamp appears wherever that item
shows. Return clears it. Both post an event; because the response carries no body, the item is re-read.

**Share and unshare.** Long-press library → Share → email, inline. Unshare is its own screen for
multi-select. Recipients get read-only access; the search index updates asynchronously.

**Auth.** Sign in (native or Google) → if `custom:Approved` is not `"true"`, PendingApproval → otherwise
the app. Google sign-in on an existing email links the identity and Cognito returns an error mentioning
"linked", which is a **success** requiring one more sign-in.

## 6. API constraints that shape this design

Facts about the backend, not preferences. Nothing in the UI may contradict them.

| Constraint | Consequence |
|---|---|
| Item listing is per-library only; `POST /search` is the sole cross-library read | No unified "all items" stream |
| Listing is alphabetical, server-grouped, `limit ≤ 50`, opaque `nextToken` | No sort or filter controls. Position is communicated by Index Letters |
| No endpoint lists lent items, and search does not match `lentTo` | Lending is surfaced in place. No "on loan" overview |
| No `createdAt` on items | No "recently added", no date sorting, no activity feed |
| No due dates | Loan duration is derived client-side from paired events. "Overdue" does not exist |
| No genre, tags, ratings or watched state | No genre browse, no filter chips, no shelves-by-mood |
| Collection endpoint returns a header but not its members | A cold link to a collection cannot load its contents; collections stay inline in the listing rather than becoming destinations |
| Mutations return empty bodies | Re-read the single item after a write instead of assuming |
| `picture` is a CloudFront URL produced asynchronously; often absent, and **synthesised from a template whenever `pictureUrl` exists without checking S3**, so a present URL may still 404 | The empty Volume Frame is a designed state. Degrade to it on load failure — never a broken-image glyph — and retry **once** on a 4s delay, then hold. The bound matters: a late thumbnail resolves on the second attempt, and a permanently missing one stops asking rather than re-requesting every 4s on every visible row. It re-arms only when the address changes, which is a new subject. Cache-bust with `?v={updatedAt}` |
| **Optional fields are `omitempty`** (`handlers/models.go`), so `lentTo`, `picture`, `order`, `collectionId` and `updatedAt` arrive **absent, not null** | Any `=== null` test is wrong. Check presence, or use `== null` so `undefined` is covered. **This governs WRITES as well as reads: a spread cannot delete an absent key** — see the patch rule below |
| **A detected candidate's `pictureUrl` can be PRESENT AND EMPTY** | `services/resolvers/google.go:99` takes the address of the thumbnail field unconditionally, so an item with no thumbnail yields a non-nil pointer to `""`; `goodreads.go:91-94` and `tmdb.go:267-270` set it only inside guards. Three resolvers, two shapes, one field. This is the single field rendered straight into an `<img src>`, and an empty src produces the broken-image glyph the design forbids — so here the row above is actively wrong: **test truthiness, not presence** |
| Renames and index updates propagate via streams (~100ms, not guaranteed) | Tolerate a just-written value not yet reflected everywhere |
| Access/ID tokens 60 min, refresh 365 days | Silent refresh; a hard expiry returns to `/login` without losing the current route |

**Patching a record from a re-read is replacement, never merge.** `{ ...row, ...fresh }` keeps a stale
`lentTo`, because a returned item comes back with the field **gone from the response rather than set to
null** — so `Mark returned` succeeded while the row went on printing `OUT`, and the reader's natural
response (tap it again) wrote **three `RETURNED` events for one loan** into an append-only ledger. A merge
is only correct when the response is a partial, and none of this API's reads are. Where a merge exists to
preserve fields the read does not return, verify that claim.

**Any probe for this must assert that an omitted field CLEARS its rendering.** A lend *adds* `lentTo` and a
spread handles that perfectly; only removal fails, so a test written on the adding direction is blind. The
same question applies to the other four fields above.

## 7. UX guidelines

**Copy.** UI strings are English; content is mixed English and French. Interface labels are uppercase;
content titles never are. Error messages name the cause and the next action. Say what a destructive action
actually does — deleting a collection orphans its items.

**Errors.** Inline and in place. Toasts are for confirmations only, never the sole report of a failed or
destructive operation.

**An error must never attribute a system fault to the reader.** A second user's first sign-in showed her
"Unauthorized" — telling her she lacked permission, when the app had failed to authenticate *itself* and
sent a request with no token. Never pass a server's status word through to a reader as though it described
them; say what the app failed to do, and give it a way to recover. **Never render `data.message` to a
reader.**

**Branch on status codes; prose is not a protocol.** `NewCollection` and `EditCollection` detected a
duplicate name by regex-matching the server's prose — and tested the wrong status besides (400, where
`collections.go` sends 409), so duplicate-name rejection had never reached the field. Treat any regex over
a server message as a defect report about the endpoint.

**Prefer the defects that cannot be reported.** A reader who cannot see a focus ring will eventually
complain; a reader shown a plausible error that blames them assumes they lack access and never mentions it.
A silent failure has no reporter, and severity should account for that.

**When you remove a value from the UI, audit every READER of it, not every renderer.** A renderer-only sweep
would have shipped the duplicate-name break above, since those forms were *parsing* the value rather than
showing it.

**Moving a control invalidates every description of where it used to live — and those descriptions sit in
files the change never touches.** After the manual escape moved out of the type sheet, `NewBook` and
`NewVideo` still named `AddItemSheet` as its home. Their *behaviour* correctly needed no change, which is
exactly why nobody opened them. The search is not "what breaks" but "what now says something false".

**A control labelled with a specific action performs that action.** A button reading `Mark returned` that
opens a menu offering Edit, Lend and Delete breaks that twice: the reader is made to choose again, from
options they did not ask for, and the one thing they did ask for is now one of three. A sheet is right when
the action genuinely needs input.

**A sheet's options are scoped by the premise of the flow that opened it.** The Book/Film sheet opened from
a collection board dropped `New collection`, whose meaning there is *discard the collection you just
chose*. Narrowing by entry point is correct when an option contradicts the premise, and wrong when it
merely seems less likely.

**A return path is not an option, and is not scoped by the premise.** `Back` is present exactly when there
is somewhere to return to — a collection board's menu swaps its body for this sheet and supplies one; the
library header's add control opens it directly and renders none. Apply the tell: *can this entry be
described without referring to another entry's answer?*

**An option that requires a parameter its siblings exist to supply is not their peer.** `Enter by hand` in
the type sheet was a peer of `Book` and `Film` while needing the very thing they supply — a type — so it
silently resolved to Book and a film could not be entered by hand at all. The sheet chooses **type only**;
the manual escape lives on `AddBook` and `AddVideo`, where the type is already known. v2 had this right.
`PRODUCT.md` requires **reachability**, not a button in the sheet, and the escape must carry the collection
through.

**Touch.** Minimum 48px targets, measured as **hit area, not element box** — a `::before` expansion is the
normal construction and the box understates the target by design. Primary actions in thumb reach. Long-press
is always duplicated by a visible affordance.

**Structure is part of being built, not a later pass.** Every authenticated screen ships with `<main>` and
an `<h1>` naming it, visually hidden where the header carries the name. Adding them while a screen is being
written is free; retrofitting across twenty screens is a chore that grows with every screen built in the
meantime. `routeLandmarks.test.jsx` enforces it.

The wider principle: **only defer what is genuinely one shared mechanism, and then do it at the first
opportunity rather than at the end.** A single accessibility pass at the end is where accessibility work
dies. Single-point fixes should be done immediately, because deferring them saves nothing.

**PWA.** `viewport-fit=cover`; safe-area padding on the header and any bottom-anchored action. Update prompt
on a waiting service worker, checked at startup, **hourly**, and on `visibilitychange` — not every 60s.

**The update prompt is load-bearing.** `registerType: 'prompt'` generates a worker whose `skipWaiting()` is
reachable only via a `SKIP_WAITING` message, and the auto-injected `registerSW.js` never sends one. Without
a prompt calling `updateServiceWorker(true)`, a newly deployed worker waits indefinitely while the old one
answers navigations **from precache** — so the CloudFront `no-cache` header on the app shell is correct and
never consulted, because the request does not reach the network. The failure is silent: the deploy succeeds
and nobody receives it.

**The prompt is not a toast.** It is a persistent, actionable notice that must survive being ignored — see
`DESIGN.md` §5, *Update Notice*.

CloudFront must serve the stable-named app shell (`index.html`, `sw.js`, `registerSW.js`, `*.webmanifest`,
`workbox-*.js`) as `no-cache`, with content-hashed `/assets/*` as `immutable`, and `/*` invalidated on
deploy. **This is already satisfied by the existing `packages/infrastructure/cloudfront.tf`. No new
Terraform is needed; do not write any.**

**Performance.** Route-level code splitting, with the scanner (`@zxing`) and the webcam loaded only by the
capture routes. **The library stream must hold 1000+ items, and windowing is REFUSED, measured twice.** The
build uses pagination at 30 plus `content-visibility`, and the profiler measures that containment as
**inert in both workloads** (−1% on the stream; −1% and −3% on a 400-row search list). What holds the stream
up is the page size. Two self-hosted variable fonts, subset to Latin + Latin Extended-A.

**Page size is a network knob as well as a rendering one, and the network side wins.** Frame-time jank
occurs at page-commit boundaries, so a smaller `limit` is the obvious lever — but `limit` also sets how many
round trips a full library costs, and the operating context is a bookshop on poor signal. At 1000 items, 30
per page is ~34 requests and 10 per page is ~100. A handful of long frames at page boundaries is accepted.

**A performance gate must be set from the observed value, not from a round number.** A gate at ten times the
observation is a comment. Set at ~1.5× the observed run and demonstrate it firing at a forced budget. Report
the commit as the **longest frame rather than a mean**, since a commit blocks the main thread and an average
would hide it; mark the response at the moment the **JSON body is parsed**, so network time is never
credited to the commit.

**PWA identity.** Icon set in the imprint's language — chrome yellow on black, a numbered volume — with
three distinct SVG sources (favicon, standard, maskable) and **no `<text>` element**, which rasterises
through fontconfig and falls back silently. Verify as **rasters**: each decodes at its declared size **and
carries the mark**, since a flat-ink 192×192 passes "decodes at 192px". Manifest `theme_color` `#0B0B0B`,
`background_color` `#F6F6F3`. **No `orientation` lock** — see `DESIGN.md` §8.

### Guard-writing rules earned the hard way

- **A new guard must be seen to fail.** Break the thing it guards, watch it go red, then fix it. A guard
  that has only ever been green is indistinguishable from a comment — and **confirm the mutation landed**,
  because a no-op `sed` and a robust guard produce identical evidence.
- **A strengthened assertion should be shown to catch what its predecessor missed**, not merely to fail.
- **Name the observable that DISCRIMINATES**, not the one the defect is named after. An assertion inherits
  the correctness of the rule it encodes *and of your model of the defect*.
- **An assertion inherits the correctness of the rule it encodes and adds nothing to it.** A test asserting
  `Enter by hand` was unconditionally present *pinned a broken control*. Writing an assertion is the moment
  to ask whether the rule is right, because afterwards the suite defends it.
- **A positive assertion cannot detect surplus.** Anywhere a check confirms presence, ask separately what
  must be absent. A manifest asserted in one direction can never report a stale entry.
- **Before excluding anything from a check, run the check without the exclusion and record what it
  reports.** If the answer is "nothing", there was never a reason.
- **A test whose fixture supplies the property under test can never disagree with a change to it.** Mock a
  real box; **hand-derive at least one expectation independently of the code that produced it.**
- **A probe for a transient state must hold that state open**, or it asserts nothing.
- **A check must not require the condition to be present in today's fixture** — assert the shape, not the
  current data — and must not pass vacuously because the fixture is too small to exercise it. Shrink the
  viewport until there is something to scroll.
- **Wait on something only the destination has.** A marker present on both origin and destination cannot
  tell you it arrived. Note the sibling trap: an `<h1>` renders during `loading`, so *the screen is here* and
  *its content is here* are different moments.
- **A probe and its consumer must resolve the same name.** `127.0.0.1` and `localhost` are not synonyms on a
  dual-stack host; the port guard declared a port free while the suite browsed a different application.
- **Never use a relative `cd` in a verification chain.** Exit 0 from the wrong directory is
  indistinguishable from a pass. Use absolute paths or print `pwd`.
- **`tee` the whole run before filtering it.** A grep is a reasonable default for a green run and the wrong
  default for a red one, and you do not know which you have until after it has scrolled.
- **A component earns a direct test the moment it gains a second construction.** Two constructions that look
  alike and obey different rules should not share a derivation.
- **When a defect's whole class is small enough to close, make the wrong construction unavailable rather
  than building a checker.** One shared helper whose **name carries the rule** beats an AST guard protecting
  a class of two.
- **Correct-by-construction is not the same as covered.** After fixing one of two siblings, the broken one
  gets a probe and the correct one keeps having none — so a later refactor can silently make it the broken
  one.
- **A fixture must contain the failure cases**, or the failure states go undesigned. The `/detections`
  fixture serves: candidates where most carry artwork and one does not; one resolver erroring while others
  succeed; a no-result response; and an `extractedTitle` that is plausibly wrong. It also carries a
  **five-candidate** response so list-length questions are reviewable.
- **A fixture written to test a judgement must not model the easy version of it.** The five-film fixture is
  five *distinct* films, not five editions of one — `search/movie?query=` matches titles, unlike an ISBN —
  because five near-identical rows read trivially as "a list" and would have biased the judgement.
- **Import a fixture's constants; never retype its values.** A wrong literal falls through the mock's *any
  other term* branch and silently tests a different state than its name claims, green throughout.
- **Where a thing genuinely cannot be tested, split it rather than waving at it.** The barcode path is three
  separable things: the **state machine** (put the decoder behind an interface so a fake drives every
  transition — this is most of the screen and fully testable); the **library binding** (feed a committed
  still of a known EAN-13 through the real decode call — the only thing that catches a broken `@zxing`
  upgrade); and the **live camera** (verified by hand, recorded as manually verified).
- **A green suite tells you nothing about what is in the diff.** Mechanical reformatting inflates a diff and
  camouflages the substantive change in it. Prefer to land a reformat and its substance separately.
- **A state that no route can reach has never been rendered.** `?as=google` and `?as=pending` exist because
  the federated account branch and `PendingApproval` were covered by unit tests and by nothing that looks at
  a screen.

### Planning and documentation rules

- **A task's acceptance criteria must restate every spec rule that task can breach**, because a rule in a
  document does not travel into a brief. The test is not "is this rule recorded somewhere" but "will the
  implementer of *this* task encounter it".
- **Prose that scopes a whole plan must not sit between two task headings.** `task-brief` extracts from one
  `### Task` heading to the next, so plan-wide context belongs above the first task heading. Two sections
  sharing a heading title collide the same way, as does a task id that is a prefix of another (`20` matches
  `20a`). Read a generated brief before dispatching it.
- **A deliberate temporary divergence is acceptable only with a named closing task and an assertion that
  will fail if it is forgotten** — a comment is not enough — and **its blast radius stated**, not just its
  existence.
- **"The destination cannot read it yet" is a fact with an expiry date.** Check *when* a premise holds, not
  only whether it does. Facts about the schedule expire.
- **The party that built a mechanism is the worst judge of whether a new ruling reaches it.** The tell is
  not that the exemption argument is weak; it is that you would not have thought of it if the code did not
  exist. Refer it, and say which way you lean. **A distinction that dissolves when an unrelated decision
  ships was never the reason.**
- **When you defer a fix, verify the fix would work.** A deferral inherits the correctness of the fix it
  names.
- **When a check and a comment collide, tighten whichever one is imprecise.** Rewording needs nobody's
  authorisation and creates nothing that outlives its reason; a scoped exception is permanent and silent.
- **Resolving an attribution question is not resolving the substantive one.** "The comp says so" explains
  why a document and the code disagree; it says nothing about whether either is right.
- **A summary of a design is not the design.** Derive from the artefact, never from a legend beside it — and
  where a legend exists it is a third thing that can drift.
- **A rule stated wider than it holds gets applied.** Check what a rule condemns, not only what it permits.
- **A number in prose is the only claim here a commit elsewhere can falsify without opening the file.**
  Counts of states, sites and files go stale silently; re-derive rather than carry them across, and derive
  with a predicate that cannot over-match.
- **The recurring defect in this project is not faulty reasoning; it is sound reasoning run against
  something nobody confirmed was the thing under test.** Font crops in the wrong face, a type scale read off
  a specimen legend, fixtures that misrepresented cover density, a hit area read as an element box, a port
  guard resolving a different name. Every one was a true answer about the wrong substrate.
- **`.impeccable/critique/ignore.md` holds corrections a prior critique already made**, so a finding
  corrected once cannot be re-filed. A prior critique's corrections are inputs to the next one, not an
  archive.

### Open

- `LibraryBrowse` has no bottom safe-area padding, so the last row of a long stream sits under the home
  indicator on an installed PWA. Recorded in `DESIGN.md` §4; nobody's ask.
- The camera *surface* is undesigned by intent — the viewport is plain, and the marks distinguishing
  scanning from decoding wait on a live feed on a device.
- A sheet confirmation swapping its body announces nothing and leaves focus where the unmounted trigger left
  it (`DESIGN.md` §6). Item detail's inline confirmation does this correctly; the four sheet ones do not.
- A suite that has been seen red once, for one unreproducible failure, is not the same as one that has
  always been green.
